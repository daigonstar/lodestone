# Security review, 25 November 2026

**Scope:** the changes for Lodestone 0.2.0 since 0.1.2: ROM libraries (EmuDeck / ES-DE folders), emulator
and RetroArch core installs, the app menu entries for emulators, RetroAchievements, libretro box art and
Steam achievements. Done with an AI coding assistant (Claude) and reviewed by the maintainer.
**Fixes ship in:** 0.2.0.

Severity uses the same scale as the [first review](2026-11-22.md): **High**, **Medium**, **Low**,
**Hardening**, plus **Note** for limits that are documented rather than fixed.

## What was checked

- **Keys.** The RetroAchievements Web API key and the Steam Web API key are only sent to their own service,
  never shown back in the interface except in a password field, and kept out of error messages
  (`net::err` and `net::get_json` drop the query string, where both keys travel).
- **Text from services.** Titles, descriptions and image addresses from RetroAchievements, Steam, GitHub
  and ES-DE's `gamelist.xml` are escaped before they reach the page, and the strict content security
  policy still applies. The "On RetroAchievements" and "On Steam" links are built by Lodestone, not taken
  from the answers.
- **Files from outside.** `gamelist.xml` image paths can't leave the system's folder (no absolute paths or
  `..`; unit test `gamelist_paths_stay_in_the_folder`). Zipped ROMs are read up to 256 MB and RetroArch
  cores up to 512 MB, so a zip bomb can't exhaust memory. libretro thumbnail names only ever become a web
  address (URL-encoded), never a file path.
- **Running programs.** Emulators start without a shell: the ES-DE launch command is split into a program
  and arguments, only emulators from Lodestone's own table can be the program, and commands that need
  ES-DE-only features are skipped. Emulator installs run `flatpak install` with a fixed Flathub app ID.
- **Network.** Every new address is in `network-hosts.txt` and the README; the network check passes.
- **Dependencies.** One new crate, `md-5` (RustCrypto). `cargo audit`: no vulnerabilities (the three
  allowed warnings are unchanged).

## Findings

### 1. settings.json was briefly readable by other users when first created: Low, fixed
- **What:** `settings.json` holds your API keys. It was written and then its permissions tightened to
  `600`, so the very first time it was created it was readable by other users on the same PC for an
  instant. Files that already existed weren't affected.
- **Fix:** it's now created with `600` from the start (`settings::save`).
- **Checked:** all tests pass. The file's permissions after a save in the app are worth confirming by hand.

### 2. Hiding an emulator's menu entry could match another app: Low, fixed
- **What:** to hide an emulator from the app menu, Lodestone looked for Flatpak menu entries whose name
  *started with* the emulator's app ID. Another app whose ID begins the same way would have been hidden too.
- **Fix:** only `<app id>.desktop` and `<app id>.<something>.desktop` match, which is how Flatpak names an
  app's entries.

### 3. RetroAchievements progress was cached readable by other users: Hardening, fixed
- **What:** `~/.local/share/lodestone/retroachievements/` keeps your achievement progress per game. It
  isn't a secret, but it is yours, and it was created with default permissions.
- **Fix:** the folder is created `700`, and existing ones are tightened at startup (`lock_down_secrets`).

### 4. RetroArch cores are checked with CRC32 only: Note
- **What:** libretro publishes a CRC32 for each core, not a cryptographic checksum. The check catches a
  broken download, but not a core deliberately swapped on libretro's server.
- **Why it stays:** there is no stronger checksum to check against. Cores come only from libretro's
  official build server over HTTPS, and the Flatpak RetroArch runs them inside its sandbox. The README
  now says this plainly.

### 5. libretro box art uses GitHub's unauthenticated API allowance: Note
- **What:** listing a system's box art takes two GitHub API requests, from the same allowance of 60 an
  hour that Lodestone uses to check its tools' checksums. A first sync with many systems could use about
  two dozen.
- **Why it's acceptable:** lists refresh at most weekly and stop at the first rate-limit answer. If the
  allowance ran out, setting up or updating a tool would fail with an error until it resets (within the
  hour); nothing is installed without its checksum.
